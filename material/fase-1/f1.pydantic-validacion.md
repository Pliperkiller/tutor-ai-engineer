# f1.pydantic-validacion — apuntes

## Sesión 6 (2026-07-29) — BaseModel, constraints y field_validator

### Por qué existe Pydantic
- En el ejercicio 02 (dataclasses) la validación se escribió **a mano** en
  `__post_init__`. Eso sirve cuando tu propio código crea los objetos.
- Un sistema real recibe datos **de afuera** (JSON de un request, config
  files, salidas de LLM): dicts con strings, sin tipos ni garantías. Antes:
  `isinstance` + conversiones + ifs por campo.
- Pydantic invierte la carga: **declaras tipos y reglas en la clase**;
  parseo + coerción + validación + errores claros salen solos. Es el motor
  de FastAPI y la base de structured outputs de LLMs (F2).

### Lo que hace distinto a `__post_init__`
1. **Coerción**: `"0.2"` (string) entra → `float 0.2` sale. Parsea antes
   de validar (`model_validate(dict_crudo)`).
2. **Errores en lote**: recolecta TODOS los errores en un solo
   `ValidationError` (con campo, valor recibido y motivo), en vez de morir
   en el primer `raise`.

### Piezas del día
```python
from pydantic import BaseModel, Field, field_validator

class ModelConfig(BaseModel):
    modelo: str                                          # obligatorio
    temperatura: float = Field(ge=0.0, le=1.0, default=0.7)
    max_tokens: int = Field(gt=0, default=1024)          # rangos SIN ifs

    @field_validator("modelo", mode="after")
    @classmethod
    def starts_with_claude(cls, value: str) -> str:
        if not value.startswith("claude-"):
            raise ValueError(f"modelo {value!r} debe empezar con 'claude-'")
        return value        # ¡obligatorio! lo devuelto es lo que se guarda
```

### El contrato del field_validator (3 partes)
1. Recibe `cls` y **el valor** del campo.
2. Valor malo → `raise ValueError` (Pydantic lo convierte a ValidationError).
3. Valor bueno → **`return` del valor**. Sin return, el campo queda `None`.

### Errores del día (corregidos por el estudiante)
- Typo `modelo='after'` por `mode='after'` → `TypeError` legible; lo halló
  leyendo el mensaje.
- **Guard invertido** en el validator (`if value.startswith(...)` sin `not`):
  2ª ocurrencia del patrón (antes: `<=` vs `<`). Hábito: leer la condición
  de rechazo en voz alta antes de correr.
- Entorno: el terminal de VS Code usaba `/usr/bin/python3` (sin pytest) en
  vez del de pyenv. Lección: los paquetes pertenecen a UN intérprete;
  `python3 -m pytest` + saber cuál `python3`. Fix definitivo: uv por
  proyecto (capstone).

### Pregunta abierta — RESUELTA en S7
Pydantic valida **cada campo por separado, envuelto en su propio
try/except**: atrapa el `ValueError`, lo convierte en registro de error,
sigue con el siguiente campo, y al final lanza UN `ValidationError` con
todos. Es *atrapar-y-acumular*, no *retener-y-soltar*.

## Sesión 7 (2026-07-30) — anidación, model_validator, serialización

### Modelos anidados
- Un campo puede tener como tipo **otro `BaseModel`**: `modelo: ModelConfig`.
  La validación recurre sola hacia adentro.
- **Dos formas de construir** el campo anidado (¡distinta semántica de error!):
  - **Forma A** — `AsistenteConfig(modelo=ModelConfig(...))`: tú construyes.
    Python evalúa argumentos ANTES de llamar → si el dato es malo, el error
    nace en el `ModelConfig` suelto → `loc = ('temperatura',)`.
  - **Forma B** — `AsistenteConfig(modelo={"modelo": ..., ...})`: pasas el
    dict crudo y **Pydantic construye por ti**, dentro de la validación del
    padre → `loc = ('modelo', 'temperatura')`. Es lo que pasa con TODO JSON
    real (`model_validate_json`).
- **`loc`**: cada registro de `e.errors()` trae `{"loc": tupla, "msg", "input"}`.
  La tupla es la RUTA desde la raíz del input hasta el dato malo; crece con
  la profundidad (incluye índices de lista: `('herramientas', 2, 'timeout_s')`).

### model_validator — reglas que cruzan campos
```python
@model_validator(mode="after")
def agente_necesita_herramientas(self):
    if self.nombre.startswith("agente-") and not self.herramientas:
        raise ValueError("un agente sin herramientas no puede actuar")
    return self          # devuelve el MODELO, no un valor
```
- Sin `@classmethod`, sin lista de campos. Recibe `self` (modelo ya
  construido, campos accesibles con punto), devuelve `self`.
- vs `field_validator`: este solo ve SU campo; `model_validator` ve todos.
- `Field(default_factory=list)` para defaults mutables: se pasa la FUNCIÓN
  (sin paréntesis) y se llama por instancia. Pydantic salva `default=[]`
  copiándolo, pero el hábito portable (dataclasses incluidas) es factory.

### Serialización y roundtrip
- `model_dump_json()` → string JSON recursivo; `model_validate_json(texto)`
  → reconstruye el árbol de objetos completo. Test de roundtrip:
  `assert reconstruido == original` (el `__eq__` generado compara campos).

### Mecánica de pytest aprendida de contrabando (tópico formal: más adelante)
- `pytest.raises(Error, match="texto")`: el match asegura que el error es
  el que el test DICE verificar, no cualquier error del mismo tipo.
- **Bug del assert muerto**: un `assert` DENTRO del bloque `with
  pytest.raises(...)`, después de la línea que lanza, NUNCA se ejecuta (la
  excepción aborta el resto del bloque) → test verde mentiroso. El assert
  sobre `exc_info` va FUERA del with.
- Auditoría clave: "¿mi test pasa por la razón que dice el docstring, o por
  otra?" (test 8 con `modelo="opus"` habría pasado por el error equivocado).
