# f1.python-profesional — apuntes

## Sesión 1 (2026-07-27) — type hints + excepciones propias

### Type hints
- `def f(x: str) -> dict[str, str]:` declara el contrato de la función.
- Beneficio: una herramienta verifica los tipos **antes** de ejecutar, y el
  editor autocompleta. Antes (sin hints) el error aparecía tarde y disfrazado.
- Sintaxis moderna (3.12): `dict[str, str]`, `list[int]` — sin `typing.Dict`.

### Excepciones propias
- `class TagError(Exception): ...` → un error **con nombre**.
- Se lanza con `raise TagError("mensaje")`.
- Ventaja sobre un `KeyError`/`ValueError` genérico: quien llama puede
  `except TagError:` y saber exactamente qué falló, sin capturar de más.

### Patrón de una función robusta
1. Firma tipada.
2. Normalizar la entrada (`.strip()`).
3. Validar y **lanzar error con nombre** si algo está mal.
4. Devolver el tipo prometido.

### Herramientas de string usadas
- `s.split(",")` → parte un string en **lista** por un separador.
- `s.strip()` → recorta espacios en los **extremos** (no separa nada).
- `s.split("=", 1)` → parte solo en el **primer** `=`. Clave para valores que
  contienen `=` (p. ej. URLs): `"url=http://a=b".split("=", 1)` →
  `["url", "http://a=b"]`.

### Control de flujo en loops
- `continue` → salta a la siguiente iteración (ignora el resto del cuerpo).
- `break` → sale del loop por completo.

### Diccionarios
- No hay `append`. Se asigna por clave: `d[k] = v` (crea o sobrescribe).

### Errores/dudas de la sesión (para repaso)
- Confusión inicial listas vs. dict ("append a un dict").
- Edge no resuelto: `split("=")` se rompe con valores que contienen `=`.
  → usar `split("=", 1)`. **Item de repaso.**

## Sesión 2 (2026-07-27) — dataclasses

### @dataclass — qué resuelve
- Antes: modelar datos con `dict` (todo string, `KeyError` ante typos, sin
  autocompletado) o una clase a mano con `__init__` lleno de boilerplate.
- `@dataclass` genera `__init__`, `__repr__` y `__eq__` a partir de los campos
  tipados que declaras. Menos código, menos bugs.

```python
from dataclasses import dataclass

@dataclass
class RunConfig:
    modelo: str
    temperatura: float
    max_tokens: int = 1024   # campo con default
    stream: bool = False
```

### Métodos mágicos (dunder) que genera
- `__repr__`: representación legible al `print` → `RunConfig(modelo='opus', ...)`
  en vez de `<... object at 0x...>`.
- `__eq__`: `==` compara **campo por campo** (por valor), no por identidad.
  Dos configs con los mismos valores son iguales → clave para `assert x == RunConfig(...)`.

### Reglas aprendidas
- Los campos **con default** van **después** de los sin default. Al revés →
  `TypeError: non-default argument follows default argument` (al importar).
- `__post_init__(self)` corre justo después del `__init__` generado: es el
  lugar para **validar** al construir y lanzar excepción si algo está mal.

### Errores cometidos (para repaso)
- `ConfigError(...)` **sin `raise`**: crear la excepción no la lanza. Falta `raise`.
- Frontera `<` vs `<=`: la regla era `max_tokens > 0` válido → inválido es
  `<= 0`. Negar bien las condiciones de borde.

### Por qué validar en __post_init__
- Un objeto inválido no debería poder existir: validar al construir hace que si
  tienes un `RunConfig`, ya sabes que es válido (fail-fast, cerca del origen).

## Sesión 3 (2026-07-27) — paquetes + uv + ruff  [CIERRE → aprendido]

### Por qué existe uv
- Antes: `pip` (instalar) + `venv` (aislar) + `requirements.txt` (a mano). Tres
  herramientas, lento, sin reproducibilidad garantizada (dependency hell).
- `uv` (Rust): una sola herramienta que aísla, instala y genera un **lockfile**
  (`uv.lock`) reproducible. `uv init`, `uv add ruff`, `uv run pytest`.

### ruff (linter)
- Lee el código SIN ejecutarlo y marca problemas de estilo/correctitud.
- Reemplaza `flake8` + `isort` + `pylint` (más rápido, una sola herramienta).
- Comando: `python -m ruff check .`  → objetivo: "All checks passed!".

### Estructura de paquete
- Un **paquete** = carpeta con `__init__.py`. Otros módulos importan desde el
  paquete sin saber en qué archivo interno vive cada cosa.
- **Imports relativos**: el `.` significa "este mismo paquete".
  `from .tags import parse_tags`, `from .config import RunConfig`.

```
aiconfig/
├── __init__.py   # exports (API pública)
├── tags.py       # parse_tags + TagError
└── config.py     # RunConfig + ConfigError
```

### `__all__` y los dos tipos de F401
- `__all__ = ["parse_tags", "TagError", ...]` declara la **API pública**:
  controla `from paquete import *` y documenta la intención (ruff lo respeta).
- Regla para un `F401 imported but unused`:
  - ¿es basura? (un `import re` que no usas, una var muerta) → **bórralo**.
  - ¿lo quieres re-exportar? (en un `__init__.py`) → **decláralo en `__all__`**.
- Matiz: `__all__` NO oculta nada; el import explícito por nombre sigue
  funcionando. Solo gobierna el `*` y sirve de documentación.

### Errores cometidos (para repaso)
- Self-import circular en `__init__.py`: `from aiconfig import ...` (el propio
  paquete) revienta en runtime. Correcto: imports relativos (`.tags`, `.config`).

### Caveat honesto del criterio_dominio
- El criterio pide "pasa ruff **y una revisión de tipos** sin errores". Ruff hace
  el lint; el código está tipado; pero un **type-checker dedicado (mypy/pyright)**
  aún no se corrió. Enganchar en `f1.apis-rest-fastapi`.
