# f1.git-flujo — apuntes

## Sesión 4 (2026-07-29) — branches, merge y conflictos (flujo local)

### Por qué existen las branches
- Antes: carpetas duplicadas (`proyecto_v2_FINAL/`) o todos commiteando a la
  misma línea de historia, pisándose.
- Una **branch** es una línea de historia paralela que nace de un commit.
  Trabajas sin romper `main`; **merge** vuelve a juntar las líneas.

### Comandos del día
```bash
git switch -c nombre       # crear branch y saltar a ella
git switch main            # cambiar de branch
git merge otra-branch      # traer los cambios de otra-branch a donde estás
git log --oneline --graph --all   # ver la historia dibujada
git branch --merged main   # qué branches ya están fusionadas
git config --global core.editor vi   # editor por defecto de git
```

### Fast-forward vs merge commit — LA regla del día
- **Una branch es solo un puntero a un commit**, no una copia de archivos.
- Merge **sin divergencia** (main no tiene commits propios desde que nació la
  branch): git no combina nada, solo **adelanta el puntero** → `Fast-forward`.
  Cero commits nuevos; la historia queda en línea recta.
- Merge **con divergencia** (ambas líneas tienen commits propios): git combina
  y el resultado vive en un **commit de merge con dos padres** (el rombo del graph).

```
sin divergencia:            con divergencia:
A──B  ← branch              A──B   ← main
↑                            \  \
main (se adelanta a B)        C──M ← commit de merge (2 padres)
```

### Conflictos
- Ocurren cuando dos branches editaron **la misma línea desde el mismo punto
  de partida**. Git compara texto, no significado: cuál valor es "correcto" es
  una decisión de negocio que no vive en ningún commit → te pregunta a ti.
- Marcadores: `<<<<<<< HEAD` (tu lado), `=======`, `>>>>>>> branch` (el otro).
- Resolver = editar el archivo dejando el contenido final decidido — un lado,
  el otro, **o una mezcla que ninguna branch tenía** — sin marcadores, y luego
  `git add` + `git commit`.
- El mensaje de ese merge commit debe **documentar la decisión y el porqué**
  (error del día: quedó el mensaje por defecto `Merge branch '...'`).

### Errores/gaps de la sesión (para repaso)

  "branch = puntero" necesitó explicación completa. **Verificar en repaso.**

## Sesión 5 (2026-07-29) — remoto GitHub y pull requests

### Por qué existen los remotos y los PRs
- Un **remote** es un alias hacia una copia del repo en otra máquina
  (`origin` = una URL con nombre). Sin remoto, la única copia de la historia
  vive en tu `.git/` local — si se borra, no hay nada que recuperar.
- **Lección en carne propia:** re-correr `setup.sh` hizo `rm -rf` del repo de
  práctica. Ni `reflog` ni `pull` salvan eso: todo lo que git sabe vive en
  `.git/`, y no había copia en ninguna otra máquina. Con un push previo,
  habría bastado `git clone`.
- El **pull request** pone una pausa de revisión entre "terminé mi branch" y
  "esto entra a main" (antes: parches por email). El PR vive en **GitHub**,
  no en tu working copy — `gh pr merge` fusiona allá y tu `main` local queda
  desactualizado hasta que hagas `git pull`.

### Comandos del día
```bash
gh repo create nombre --public --source=. --remote=origin
git push -u origin main        # sube SOLO la branch que le pides
git branch -r                  # branches remotas conocidas
git branch -vv                 # a qué apunta cada branch + tracking + ahead/behind
gh pr create --title "..." --body "..."   # parado en la branch del cambio
gh pr merge --merge            # fusiona EN GitHub (desde cualquier branch)
git reset --hard origin/main   # retrocede main a lo que hay publicado
```

### Reglas del día
- `origin/main` es **otro puntero más**: "hasta dónde sé que llegó el remoto".
  Push lo mueve hacia ti; pull te trae hacia él. Mismo modelo de punteros.
- El commit cae en la branch donde está **HEAD**, no en la última creada.
  Error del día: branch `docs-parametros` creada, commits hechos en `main`
  → gh intentó un PR "main into main". Reparación: ff-merge de main a la
  branch + `reset --hard origin/main` en main.
- **GitHub `--merge` SIEMPRE crea un commit de merge**, aunque git local
  haría fast-forward. Es trazabilidad: `Merge pull request #1...` ancla la
  historia al PR (discusión, review, porqué).
- En un fast-forward **no se crea ningún commit**: solo avanza el puntero.
  (Gap de S4 cerrado: lo explicó 2 veces con sus palabras.)
